# CLAUDE.md

Personal assistant on self-hosted n8n. It reads Gmail, LinkedIn notification emails and
Telegram messages forwarded to a private bot, turns anything that needs attention into
tasks in Notion, prepares Gmail reply **drafts**, and sends a morning digest to Telegram
with a feasibility check against the calendar. The assistant prepares and suggests; the
owner decides and sends.

Read first: `PRD.md` (product), `docs/PLAN.md` (build order and phases),
`docs/PRD-REVIEW.md` (design decisions that deviate from or refine the PRD),
`docs/SETUP.md` (what the owner has set up so far).

**It runs on the owner's n8n Cloud instance**, reached through the n8n connector (MCP). The
self-hosting files in `infra/` are an unused alternative. The instance also holds seven
pre-existing test workflows ("My workflow …", "Gmail app"): leave them alone.

## Hard rules

1. **No send operation, ever.** No Gmail `send`/`reply`/`sendAndWait`, no `emailSend` node,
   no HTTP call to a send endpoint. Drafts only. `npm run check` enforces this and
   `npm run deploy` refuses to push when it fails.
2. **Telegram writes only to the owner's chat.** The chat ID always comes from config,
   never from an incoming message.
3. **Never change dates, priorities or statuses in Notion automatically**, except:
   creating items (WF0), closing FYI items after a digest was delivered (WF3), and
   closing tasks the owner ticked on the "Сегодня" page before the next digest (WF3,
   mirroring her own decision; approved 2026-10-12).
4. **No secrets or personal data in git.** Credentials live only in n8n. Ignore and
   exclusion lists, chat IDs, database IDs and the public hostname live in
   `config/config.local.json` and `infra/.env`, both gitignored. Built workflows in
   `build/` contain config and are gitignored too. Exported workflow JSON is sanitized by
   `npm run export` before it lands in `workflows/`, and `npm run check` rejects committed
   JSON with credential IDs, webhook IDs, filled inject blocks or personal email addresses.
   The repo is meant to be shareable as a sample.
5. **The repo is the source of truth.** Prompts, Code-node logic and config are edited
   here and injected into workflow JSON by `npm run build`. Never edit them in the n8n UI;
   the next deploy overwrites UI edits. Node layout and wiring may be edited in the UI and
   brought back with `npm run export`.
6. **Ask before destructive actions on live systems**: deleting, archiving or unpublishing
   workflows on the instance, changing the schema of a populated Notion database.
7. **Privacy exclusion list runs before any model call**, Jev included. Notion stores a
   summary and a link, never a full message body.

## Working style

- **Simple and incremental.** Small steps; run `npm test` and `npm run check` after each
  one before moving on. Do not overengineer and do not program defensively: validate at
  the boundaries (config, API responses) and let the rest assume valid input. Try/catch
  only where a failure is expected and handled.
- **Root cause before fix.** Reproduce the problem consistently and prove it with
  evidence (a failing test, an execution log, a response body) before changing code. One
  hypothesis at a time. No workarounds for bugs in our own code; platform limitations go
  to the friction log instead.
- **Latest APIs.** Use the current n8n SDK, node versions, Claude API and Notion API as
  documented now (the n8n connector's SDK reference, `claude-api` skill), not from memory.
- **Style.** Short modules and functions with clear names. JSDoc one-liners on exports,
  few comments elsewhere. No emojis in code, logs or console output. Keep `README.md`
  concise.

Tooling is Node.js 20+ with **no dependencies** (built-in `fetch`, `node --test`).

## Commands

```
npm test                         # unit tests
npm run build                    # workflows/*.json → build/*.json with src, prompts, config injected
npm run check                    # no-send, retry and hygiene checks (also run by deploy and CI)
npm run deploy -- WF1            # build + check + create/update + activate one workflow
npm run deploy -- all --dry-run  # show what would change, write nothing
npm run export                   # pull from n8n, sanitize, empty inject blocks, write workflows/
```

**Workflows are built through the n8n connector**: read its SDK reference and
best-practice notes first, create or update the workflow, validate, test-run, then publish.
The JSON toolchain above is the fallback and the hygiene gate: anything exported to
`workflows/` must pass `npm run check`. Deploy and export over the public API need
`N8N_HOST` and `N8N_API_KEY` in the environment settings and the host on the network
allowlist; only set that up if the connector cannot do something.

**Notion is managed through the Notion MCP connector**, not scripts: create the databases
from `notion/schema.json`, query items for checks and the Jev-vs-Haiku comparison. Write
the resulting database IDs into `config/config.local.json`. n8n uses its own Notion
integration token, stored as an n8n credential.

## Workflow conventions

- Names: `WF1 Email Triage`, `WF2 Telegram Intake`, `WF3 Morning Planner`,
  `WF4 Error Handler`. **The published email triage is `WF1b Email Triage (agent)`**
  (`workflows/WF1b-email-triage-agent.json`, AI Agent node, native Gmail and Notion
  nodes) since 2026-10-13; `WF1` is unpublished and kept as the HTTP-Request alternative.
  Changes to the triage logic go to WF1b first. Build order is WF4 → WF2 → WF1 → WF3 (simplest end-to-end path
  first). The shared steps **Upsert** (WF0 in the PRD) and **Decide** (WF5 in the PRD) are
  node groups reused inside WF1 and WF2, not separate workflows: on n8n Cloud every
  sub-workflow call counts against the 2 500 executions per month.
- **Injection convention.** Inside a Code node, a block

  ```js
  // @inject src/capacity.js as capacity
  // @end-inject
  ```

  is filled at build time with the module wrapped as an object of its exports
  (`capacity.computeCapacity(...)`). `prompts/<name>.md as PROMPT` becomes the parsed prompt
  object and `config as CONFIG` the config. The glue code around the block (reading
  `$input`, returning items) lives in the workflow JSON; the logic lives in the repo.
  Committed JSON keeps the blocks empty; `npm run export` empties them again.
- `src/` modules are pure: named inline exports only, no imports, no n8n globals, no
  network. A test runs every module in a bare VM context, so this is enforced.
- Every workflow has a `Config` Code node (`// @inject config as CONFIG`) so settings
  are in one place. Secrets never go there: they are n8n credentials.
- If a sub-workflow is ever needed, committed JSON references it as `name:<workflow
  name>`; deploy resolves names to live IDs, export turns IDs back into names. Deploy also
  sets WF4 as each workflow's error workflow and keeps credentials attached in the UI.
- **The "Сегодня" page** (`config.notion.today_page_id`) is the owner's single view: WF3
  rewrites it every morning (summary, the plan as to-dos with page mentions, then the other
  open tasks under Завтра / На этой неделе / Когда-нибудь) and, before planning, closes the
  tasks whose to-dos she ticked. Logic in `src/today-page.js`; the Notion API has no
  "replace children", so old blocks are deleted one by one, then the new ones appended.
- Every Notion write goes through the Upsert group (idempotent on `Source ID`). Every
  classification goes through the Decide group. Claude calls use the HTTP Request node, or
  the n8n Anthropic node through n8n Cloud's gateway credits if it supports
  `output_config` structured output; decide once in Phase 4 and record it in `docs/NOTES.md`.
- External-API nodes (HTTP Request, Notion, Gmail, Telegram, Google Calendar): "Retry on
  fail" on with at least 3 tries; `npm run check` enforces it. Telegram nodes target
  exactly `={{ $('Config').first().json.telegram.owner_chat_id }}`, also enforced. `WF4` is the error workflow
  for every other workflow.
- Deterministic things (dedup, filtering, date math, capacity arithmetic, trimming the plan
  to fit) are code. Judgment (classification, summaries, drafts, prioritization) is a model.

## LLM rules

- Model IDs are config, never hard-coded in nodes:
  `claude-haiku-5-5` (triage, enrichment, drafts), `claude-sonnet-5-5` (planner);
  `claude-opus-5-5` is the planner upgrade if quality is not good enough.
- Endpoint `POST https://api.anthropic.com/v1/messages`, headers `x-api-key`,
  `anthropic-version: 2023-06-01`, API key from the n8n credential. Build the body with
  `src/claude.js` (`buildClaudeRequest`) and read it with `parseClaudeResponse`, which
  turns refusals and `max_tokens` truncation into errors.
- Always structured output:
  `output_config: { format: { type: "json_schema", schema: {...} } }` with
  `additionalProperties: false` and every field in `required`. The first `text` block is
  valid JSON. Keep the schema next to the prompt in `prompts/`.
- Thinking is adaptive by default on these models. Set `output_config.effort`:
  `low` for triage/enrichment, `medium` for drafts, `high` for the planner.
  `max_tokens` must leave room for thinking: 1024 triage, 2048 drafts, 8000 planner.
- Do **not** set `temperature`, `top_p`, `top_k` (400 on Haiku 5.5). No assistant prefill.
- Read response content by block `type`, never by index.
- Bound inputs: email bodies truncated to ~6k characters before the call; the planner
  sees at most 40 candidate tasks.
- Language: drafts in the language of the incoming message; task titles and digest in
  Russian unless config says otherwise.

## Jev (TypeSafe AI) rules

- The Decide group answers four typed questions: `action_needed` (noul), `action_type`
  (choice: `email_reply` / `other`), `priority` (choice P1–P3), `estimate` (choice
  15/30/60/120). Jev is called by HTTP Request (`POST /v1/systemone`, `model: jev-latest`);
  base URL is config so OpenRouter's `/api/v1/systemone` can stand in.
- `DECIDER_MODE` in config: `haiku` (Claude only, default on day one), `shadow` (call both,
  act on Haiku, store both), `jev` (Jev primary; fall back to Haiku on HTTP error, 10 s
  timeout, or `max(p, 1-p) < CONFIDENCE_THRESHOLD` for `action_needed`).
- Every item records `Decided by` and `Confidence`; in shadow mode also `Shadow decision`.
  Haiku's confidence is self-reported, not calibrated: never compare the two as equals.
- Jev never produces free text. Titles, summaries, due dates, drafts and plans are Claude.

## n8n gotchas

- No Variables (`$vars`) on the Cloud Starter plan or in Community Edition, so config is
  injected at build time into `Config` nodes. Nothing needs `$env`.
- n8n Cloud Starter: 2 500 executions per month, and workflows pause when it runs out. No
  sub-workflows, no polling faster than every 30 minutes; a poll with no new mail is not an
  execution.
- The Notion node has not reliably supported the `status` property type. `Status` is a
  `select` in `notion/schema.json`. If a Notion node cannot do something, use an HTTP
  Request node with the same Notion credential rather than fighting the node.
- Gmail "Create Draft": pass `threadId` and the exact `Re: <subject>`. Verify once that the
  draft threads correctly; if not, create the draft through the Gmail API with a raw MIME
  message carrying `In-Reply-To` and `References`.
- Telegram messages are limited to 4096 characters: `src/digest-format.js` splits by section.
- Gmail Trigger polls new mail only; its query excludes promotions, forums, spam and own
  sent mail. Notion `Source ID` is the idempotency guard. The assistant puts **no labels**
  on mail (the owner found `assistant/*` labels visual noise, 2026-10-13); WF1 still
  carries the label nodes as the unpublished alternative.
- Self-hosting only (`infra/`): SQLite with execution pruning; backups are a tar of the
  n8n volume.

## Data model

`notion/schema.json` is authoritative. `Source ID` formats: Gmail `gmail:<messageId>`,
LinkedIn `linkedin:<gmail messageId>`, Telegram `tg:<chat_id>:<message_id>`, manual items
empty. Manual tasks need only a Title; defaults are P2 and 30 minutes.

## Cost guardrails

Target is under €15/month for hosting plus models; expected is €6–7. Rule pre-filter
before any model call, bounded inputs, one planner call per day, no polling faster than
30 minutes. If a change adds a model call per email, say so in the PR or commit message.

## Friction log

Whenever an n8n limitation forces a workaround, append a dated entry to `docs/NOTES.md`
(what was tried, what failed, what was done instead). This is a PRD success metric.

## Git and merging

- Work on the assigned feature branch; commit small, descriptive, imperative messages.
- Never commit `config/config.local.json`, `infra/.env`, backups or unsanitized exports.
- **The owner has authorized Claude to merge its own pull requests into `main`** without
  asking, once all of these hold:
  1. `npm test` and `npm run check` pass locally and the CI workflow is green on the head commit;
  2. a code-review pass over the full diff found no unresolved correctness, safety or
     privacy issue (hard rules above);
  3. the PR has no merge conflict and no open review thread from a human.
  Merge method: squash. After merging, restart the feature branch from the new `main`.
- Changes to the live n8n instance or Notion data are not covered by this rule; hard rule 6
  still applies.
